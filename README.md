# AuditBox

**面向 Linux 服务器和网络设备的本地智能运维与审计工作台。**

[![License: GPL-3.0-only](https://img.shields.io/badge/License-GPL--3.0--only-blue.svg)](LICENSE)
[![Python 3.10 / 3.11](https://img.shields.io/badge/Python-3.10%20%7C%203.11-3776AB.svg)](CONTRIBUTING.md)
[![Hugging Face Models](https://img.shields.io/badge/Hugging%20Face-Models-FFD21E.svg)](models/README.md)

AuditBox 将设备连接、浏览器终端、命令辅助、AI 助手、执行确认和关联审计整合在一个工作台中。运维人员可以在这里连接服务器或交换机，查找并执行命令，理解设备输出，让助手协助排查，并在任务结束后追溯操作过程。

项目围绕一次运维操作的完整过程组织能力：**操作前提供命令与风险依据，操作时保留人工确认和设备原生交互，操作后关联任务、审批、命令与执行记录。** 人工输入和 Agent 终端操作复用已有连接，经过相同的命令控制与审计链路。

当前仓库提供网页、终端代理、智能助手、审查服务、模型运行配置和部署工具。默认常驻部署面向 Linux x86_64 主机，问答与命令审查模型在本机运行，浏览器通过统一入口访问工作台。

## 项目用途

AuditBox 面向需要经常进入设备命令行、核对变更影响并保留操作依据的运维人员与设备维护者。

| 场景 | 要完成的工作 | AuditBox 提供的支持 |
| --- | --- | --- |
| Linux 日常排障 | 检查磁盘、内存、进程、服务与网络状态 | 浏览器终端、命令速查、输出解释与后续检查建议 |
| 网络设备巡检 | 根据设备平台查看接口、路由和配置 | 平台命令补全、操作卡片、参数化模板与近期操作推荐 |
| 需要确认的变更 | 核对命令作用范围，再决定是否提交 | 确定性命令规则、一次性确认、取消与硬阻断 |
| AI 辅助运维 | 让助手理解问题、读取信息并协助操作 | 问答、附件上下文、按需启用的工具与逐次执行审批 |
| 操作复盘 | 解释谁提出任务、谁批准、发出了什么命令 | 关联登录、终端会话、Agent 对话、审批与执行记录 |

### 部署在哪里，连接什么

使用时会涉及三个位置：

- **操作员浏览器**：展示终端、命令辅助、助手和审计界面。
- **AuditBox 主机**：运行网页入口、协议代理、Agent、审查服务与本地存储；完整本地 AI 部署还在此运行模型。
- **目标设备**：通过 SSH、Telnet 或宿主机可用串口连接的 Linux 服务器、交换机等设备。

AuditBox 主机使用已有网络访问目标设备。目标的登录账号、可执行权限与命令语法仍由目标系统决定，连接时需要选择对应的设备平台。串口访问还取决于宿主机设备与服务账号权限。

## 一次运维任务如何完成

以排查一台 Linux 主机的磁盘占用为例，可以按下面的过程理解工作台中的各项能力。涉及助手的步骤需要先配置 AI 服务。

1. **连接目标。** 操作员登录工作台，新建设备连接，选择 Linux 平台并填写目标地址、端口和登录凭据。Gateway 和 Proxy 建立终端会话，后续手工输入和 Agent 操作使用这条已有连接。
2. **查看当前状态。** 在终端执行 `df -h` 等只读命令，查看设备返回的真实输出。命令辅助提供补全、速查与下一步检查提示，操作员可以继续沿用远端 CLI 的 Tab、历史导航和行编辑。
3. **让助手解释问题。** 将相关输出提供给助手，询问磁盘使用情况和排查思路；也可以上传当前任务的参考文件。问答模式结合问题、历史与相关附件摘录生成回答，实时设备判断需要当前设备输出。
4. **按需开启 Agent 执行。** 开启执行开关与所需能力后，助手可以提出工具调用。操作员检查目标、命令和预期影响，再批准或拒绝终端写入。工具通过 Gateway 复用当前终端，返回实际输出供助手继续判断。
5. **核对需要变更的操作。** 涉及清理或服务变更时，提交的命令继续经过 Proxy 的确定性规则。命中确认规则时再次确认，命中硬阻断规则时停止下发；旁路审查在后台分析近期操作并补充风险建议。
6. **回看执行过程。** 在审计中查看命令来源、确认与取消、下发状态、输出摘要及关联任务。只观察到断连、输出静默或缺少可靠退出状态时，结果保留为未知。

这个过程把“提出建议”“批准动作”“命令下发”和“取得执行结果”分别记录，便于在排障、变更和复盘时核对事实。

## 主要能力

### 设备连接与原生终端交互

工作台提供多标签浏览器终端，支持 SSH、Telnet 和宿主机可用串口，并保存设备信息、常用连接与最近连接。设备大类和平台决定后续使用的命令资料与规则。

目标 CLI 继续处理普通输入、Tab 补全、历史导航、行编辑和分页。AuditBox 在命令提交边界检查待执行内容，终端仍保留设备原有的操作习惯与输出形式。

### 从查命令到确定下一步

命令辅助由几类不同用途的能力组成：

| 能力 | 帮助解决的问题 |
| --- | --- |
| 前缀补全 | 已知命令开头时，查找可用语法和候选命令 |
| 行为图推荐 | 结合当前会话和近期操作，查看可能的下一步检查 |
| 速查卡片 | 按用途浏览常用操作，了解命令含义、参数与注意事项 |
| 参数化模板 | 填入目标参数，生成需要提交到终端的命令 |

参考资料保留语法、型号、视图和来源信息。操作员选用的命令与模板生成结果统一进入终端控制链路，提交时继续检查规则。

### 执行前确认与后台风险审查

命令提交时，命令闸门根据确定性规则决定允许、请求确认或阻断。确认界面用于核对当前待执行命令；命令改变后重新检查，普通确认不能解除硬阻断。

旁路审查分析近期命令及其上下文，用于解释操作的潜在影响和跨命令关联。Linux 可调用专用审查模型，其他平台使用已配置的规则或模型能力。审查结果关联到操作记录，供当前操作和后续审计参考。

命令下发由确定性规则与确认状态控制。模型生成的风险建议和候选命令，需要结合目标状态与操作目的核对；未命中规则的命令可能按未知项放行。

### 问答、增强问答与 Agent 执行

助手的交互方式与工具权限分别配置：

| 工作方式 | 用户可以做什么 | 执行条件 |
| --- | --- | --- |
| 标准问答 | 解释命令和输出，分析问题，整理可手动执行的排查步骤 | Agent 与问答模型可用 |
| 增强问答 | 使用增强思考参数处理问题，沿用相同的问答上下文规则 | 与标准问答共用问答模型，通过请求参数切换 |
| Agent 工具执行 | 让助手读取允许访问的信息、提出操作，并依据工具结果继续任务 | 开启执行总开关、启用相应能力，并按工具策略审批 |

Agent 执行初始关闭，重启后沿用用户保存的设置。启用执行后，终端写入和 Ctrl+C 需要逐次工具审批；通过工具审批的命令仍会进入命令闸门。

Agent 通过已有终端的内部工具接口读写设备，不持有目标 SSH 密码，也不另建第二条连接。人工输入可以中断正在等待结果的 Agent 操作，后续步骤以实际返回状态为依据。

### 任务资料、知识库与扩展工具

对话文件区支持 Markdown、TXT 和 DOCX。文件归属当前对话，服务端提取规范化文本，并按问题提供有限的相关摘录；开启执行后，Agent 还可以按能力检索和分段读取。问答模式不会自动取得完整实时终端转录，分析设备现状时需要提供当前输出。

可选知识库用于较长期参考资料的检索，需要额外的 Embedding 配置和依赖，默认关闭。对话附件与知识库分别管理，具体格式与导入范围见 [Agent 说明](agent/README.md)。

扩展能力包括本地 Skill、通过 MCP 接入的外部工具，以及按配置启用的代码、Docker、SQL 和文件生成工具。各能力可以独立启停，工具挂载受 Agent 执行总开关控制，调用遵循相应审批策略。外部连接能够访问的系统与数据由其配置决定。

### 从任务到命令的关联审计

审计按登录、输入、执行和行为组织记录。每条命令关联设备、终端会话、输入来源和执行状态；Agent 操作进一步关联原问题、对话、运行与审批者。

| 需要核对的事实 | 对应信息 |
| --- | --- |
| 操作从哪里产生 | 人工输入、速查或 Agent 来源，以及关联的登录和会话 |
| 操作是否获准 | 工具审批、命令确认、取消与阻断记录 |
| 命令是否下发 | 对应执行记录的下发状态 |
| 设备返回了什么 | 经过脱敏且有长度限制的输出摘要 |
| 是否能够确认完成 | 可靠的执行状态；证据不足时保留未知结果 |

新记录保存结构化操作与有限输出摘要，原始终端输出字节流不作为新记录完整持久化。界面展示与导出用于回溯操作依据；记录关系、增量读取和历史格式转换见[关联审计设计](docs/linked-audit.md)。

## 选择运行方式

可以根据当前要体验的能力，逐步增加运行部分：

| 目标 | 需要运行的部分 | 可以使用的能力 |
| --- | --- | --- |
| 先体验核心工作台 | 网页、Gateway、Proxy | 设备终端、命令辅助、确定性确认与阻断、关联审计 |
| 增加 AI 问答 | 核心工作台、Agent、可用的问答模型端点 | 标准／增强问答、当前任务的资料上下文 |
| 增加 Linux 模型审查 | 核心工作台、Inference、Linux 审查模型，并启用旁路审查 | 近期命令上下文分析与关联风险建议 |
| 使用 Agent 操作设备 | AI 问答、活动终端、已启用的工具能力与执行开关 | 经过审批的工具执行与多步任务 |
| 在服务器常驻运行 | systemd 应用服务；默认本地模型使用 Docker Compose 与 NVIDIA GPU | 统一启动、健康检查、持久化配置与版本管理 |

QuickStart 覆盖第一种方式。完整默认 AI 部署使用问答与 Linux 审查两个模型，H3C 专用审查、知识库和扩展工具按需启用。GPU 资源需求与模型、上下文和并发配置有关，默认两个模型共享显存与算力。

## QuickStart

需要 **Bash、uv、Python 3.11，以及 Node.js 20.19+ 或 22.12+**。在终端执行：

```bash
git clone https://github.com/Motannier/auditbox.git
cd auditbox
./scripts/quickstart.sh
```

脚本按锁文件安装依赖、构建网页、初始化配置，并在当前终端启动 Proxy 和 Gateway。浏览器访问 **http://127.0.0.1:18080**，按 **Ctrl+C** 停止本次启动的服务。

> [!NOTE]
> QuickStart 提供终端、命令辅助、执行确认与审计，无需 GPU 或模型。AI 问答、Agent 和模型旁路审查按[模型说明](#模型与运行方式)与[部署文档](deploy/server/README.md)单独配置。

### 首次登录与连接

1. 在 `box/.env` 中查看 `AUDITBOX_ADMIN_PASSWORD` 和 `AUDITBOX_SUPER_ADMIN_PASSWORD`，分别对应 `opsadmin` 与 `superadmin`。
2. 使用 `opsadmin` 登录，新建连接，填写可达目标的 IPv4 地址、SSH 端口和登录凭据，并选择对应设备平台。
3. 打开终端，执行一条只读命令，查看命令辅助与操作记录。`superadmin` 可查看和导出审计。

首次运行生成独立的随机密码和登录签名密钥，保存在权限为 `0600` 的 `box/.env`。脚本保留已有配置，不打印密码；核心工作台的数据与日志保存在 `box/data/`。

| 后续操作 | 命令 |
| --- | --- |
| 使用现有环境启动 | `./scripts/quickstart.sh --start-only` |
| 仅安装依赖、构建与初始化 | `./scripts/quickstart.sh --build-only` |
| 使用 Python 3.10 构建 | `PYTHON_VERSION=3.10 ./scripts/quickstart.sh` |

服务默认仅监听回环地址。在远程主机运行时，可通过 SSH 本地端口转发访问：

```bash
ssh -L 18080:127.0.0.1:18080 user@server
```

### 从核心工作台启用 AI

准备好所需模型端点后，启动 Agent 以提供问答；需要 Linux 模型旁路审查时，再启动 Inference 并配置审查端点。QuickStart 初次配置关闭历史旁路审查，启用时将 `box/.env` 中的 `AUDITBOX_HISTORY_REVIEW_ENABLED` 改为 `true`，并重启 Proxy。

本地开发的服务入口见[本地开发](#本地开发)，常驻运行的完整安装与启动步骤见[构建与部署](#构建与部署)。Agent 工具执行通过界面的执行开关与能力设置另行启用。

## 模型与运行方式

问答模型与审查模型承担不同任务。问答模型供 Agent 生成回答、计划和工具调用；审查模型用于后台分析近期设备命令及其上下文。

| 用途 | 模型来源 | 默认配置 |
| --- | --- | --- |
| 标准／增强问答与 Agent | [MiniCPM5 2B GGUF](https://huggingface.co/openbmb/MiniCPM5-2B-GGUF) | `minicpm5-2b`，Q4_K_M，32,768 tokens 上下文 |
| Linux 命令风险审查 | [Command Guard 0.8B Q8_0](https://huggingface.co/Motanni/auditbox-command-guard-0.8b-gguf) | `command-guard`，10,240 tokens 上下文 |
| H3C Comware 命令风险审查 | [H3C Risk 0.8B Q8_0](https://huggingface.co/Motanni/auditbox-h3c-risk-0.8b-gguf) | 可选模型，需要单独配置端点与路由 |

两个 0.8B 模型是基于 Qwen3.5-0.8B 的领域微调制品，采用 GPL-3.0-only，并保留基础模型的 Apache 2.0 许可与归属说明。MiniCPM5 使用上游官方制品。

默认本地推理通过两个 llama.cpp CUDA 容器提供 OpenAI 兼容接口。Agent 直接调用问答端点，Proxy 的 Linux 旁路审查经 Inference 调用审查端点。Inference 的排队与调度只作用于经过它的请求。

- **下载与校验**：[模型说明](models/README.md)提供固定版本下载地址；[模型清单](models/manifest.json)记录文件名、revision、大小和 SHA-256。
- **用途与边界**：见 [Linux 模型卡](models/model-cards/command-guard/README.md)和 [H3C 模型卡](models/model-cards/h3c-risk/README.md)。
- **替换模型端点**：应用支持 Ollama 和其他 OpenAI 兼容端点，需要核对模型地址、别名、聊天模板、工具调用支持、上下文与输入预算。外部模型和扩展服务的数据访问范围由连接配置决定。

## 系统架构

工作台由网页、四个应用进程、模型服务和本地存储组成。Agent 进程负责对话、上下文与工具生命周期，模型服务负责实际推理。

![AuditBox 架构](docs/images/architecture.svg)

| 组件 | 它负责什么 | 主要交互对象 |
| --- | --- | --- |
| 网页工作台 | 设备连接界面、终端、命令辅助、助手与审计展示 | Gateway |
| Gateway | 登录鉴权、网页与 API、WebSocket 会话、助手转发和内部终端工具桥 | 浏览器、Proxy、Agent |
| Proxy | SSH／Telnet／串口连接、命令恢复、确认与阻断、执行审计 | Gateway、目标设备、Inference |
| Agent | 模型对话、上下文管理、工具审批、运行持久化与扩展能力 | Gateway、问答模型、启用的外部工具 |
| Inference | 设备模型路由、请求排队与经过本服务的推理调度 | Proxy、审查模型 |
| 模型服务 | 提供问答或设备命令风险分析的推理接口 | Agent 或 Inference |
| 本地存储 | 保存业务状态、审计、对话、运行与审批记录 | 相应应用进程 |

### 主要请求如何流转

- **人工终端操作**：浏览器经 Gateway 将输入交给 Proxy，Proxy 检查提交的命令后访问目标设备，再把输出沿原会话返回。
- **AI 问答**：浏览器经 Gateway 调用 Agent，Agent 组装上下文、请求问答模型，再把回答流式返回界面。
- **Agent 终端执行**：Agent 保存工具调用并等待审批，批准后经 Gateway 的内部工具桥操作已有 Proxy 会话，取得输出后继续任务。
- **旁路风险审查**：Proxy 将近期操作交给 Inference 和已配置的审查端点，审查结果返回后关联到操作与审计记录。

### 默认端口与访问范围

| 服务 | 默认地址 | 用途 |
| --- | --- | --- |
| Gateway | `127.0.0.1:18080`；常驻安装另绑定指定服务器 IP | 浏览器统一入口 |
| Proxy | `127.0.0.1:19000`；同进程事件通道 `19001` | 终端代理与辅助事件 |
| Agent | `127.0.0.1:18765` | 问答、上下文与工具运行 |
| Inference | `127.0.0.1:18091` | 设备模型路由与审查调度 |
| 问答模型 | `127.0.0.1:18081` | 标准／增强问答与工具调用生成 |
| Linux 审查模型 | `127.0.0.1:18082` | Linux 命令上下文分析 |

完整部署由 systemd 管理应用进程，以 Docker Compose 运行默认本地模型。Gateway 对浏览器进行鉴权；Agent 没有独立登录鉴权，内部应用与模型端点保持回环监听。

业务与审计记录保存在 SQLite，Agent 使用独立的会话、运行、审批和知识元数据存储。Agent 当前以配置中的固定本地用户保存会话，部署与共享使用时应了解这一归属方式。完整进程、数据路径和启动依赖见[系统架构](docs/ARCHITECTURE.md)。

## 关键设计

### 在命令提交边界检查，保留原生 CLI 交互

终端输入包含逐字编辑、历史命令、Tab 补全和远端重绘。Proxy 在 Enter 提交时暂扣提交动作，恢复当前待执行命令，再检查规则；普通输入和行编辑继续由目标 CLI 处理。

平台适配器分别处理提示符、清行和分页语法。操作员可以沿用设备的原生交互，并在真正提交命令前核对需要确认的内容。

### 用规则控制下发，用上下文补充风险依据

命令闸门根据确定性规则和确认状态决定命令如何下发：

| 决策 | 行为 |
| --- | --- |
| 允许 | 按当前规则继续下发 |
| 确认 | 保存待执行命令与一次性确认状态，等待批准或取消 |
| 阻断 | 停止下发并显示原因，普通确认不能解除硬阻断 |

确认只对当前待执行命令生效；命令变化后重新检查。规则覆盖取决于设备平台、资料和具体命令，未命中项可能按未知项放行。

旁路审查在后台分析近期操作，适合补充连续命令的影响、设备上下文与风险原因。模型输出进入提示与审计链路，命令闸门和用户确认负责下发决策。

### Agent 与人工操作复用终端和控制链路

Agent 工具通过 Gateway 持有的活动会话读写终端，沿用已有目标、连接状态和命令规则。操作员可以看到工具要访问的目标与写入内容，再决定是否批准。

```text
操作员提出任务
  → Agent 生成工具调用，保存待审批参数
  → 操作员批准或拒绝
  → Gateway 检查执行开关和活动终端
  → Proxy 检查命令规则与确认状态
  → 目标设备执行，输出与状态返回 Agent
  → 后续步骤继续参考真实工具结果
```

终端写入和 Ctrl+C 均需逐次工具审批。工具审批与危险命令确认分别记录；人工输入可以中断正在等待的 Agent 操作。详见[终端工具设计](agent/docs/TERMINAL_TOOL_DESIGN.md)。

### 保留上下文与审批，支持中断后恢复

模型输入按稳定提示、已有历史和当前上下文组织，变化后的目标、文件信息和时间放在后部。接近输入预算时，Agent 压缩较早历史，保留任务约束、已执行证据、未完成步骤与审批状态；压缩后仍超出预算时明确报错。

工具暂停时保存名称、参数与运行检查点，继续请求提交批准或拒绝决定。服务端沿用保存的参数与历史恢复任务，保留失败、取消和待审批状态。附件与知识库按当前任务提供相关内容，历史输出与快照仍需要结合当前设备状态核对。

上下文、附件摘录和恢复规则见 [Agent 说明](agent/README.md)。

### 审计关联任务来源与实际执行事实

登录、输入、执行和行为记录关联到设备、会话和命令。Agent 操作还关联原问题、对话、运行与审批者，便于核对一次任务中的建议、批准、取消、下发与结果。

业务记录更新与递增审计变更日志在同一事务中提交，增量读取按序列游标推进。Agent 会话和运行使用独立 SQLite 持久化，终端记录保留经过脱敏且有长度限制的输出摘要。

无法取得可靠退出状态时，结果记为未知；仅观察到断连或静默时保留这一限制。相关数据关系和历史记录处理见[关联审计设计](docs/linked-audit.md)。

## 设备适配与扩展

连接协议负责传输，设备平台决定命令语法、推荐与风险规则。运行时按操作员选择的 `device_type` 和 `device_profile` 加载平台能力。

| 设备大类 | 平台标识 | 适配对象 |
| --- | --- | --- |
| `server` | `linux` | Linux 服务器 |
| `switch` | `h3c_comware` | H3C Comware |
| `switch` | `huawei_vrp` | 华为 VRP |
| `switch` | `cisco_ios` | 思科 IOS／IOS XE |
| `switch` | `zte_zxr10` | 中兴 ZXR10 |

平台适配覆盖命令资料、参数模板、操作推荐和规则等不同部分，具体能力依赖资料覆盖、目标型号与软件版本。协议类型本身不能代替设备平台信息；连接交换机时需按实际系统选择平台。

设备能力包采用纯数据格式，可补充平台资料与命令能力。超级管理员在无活动终端时导入，应用检查大小、结构、引用与 SHA-256，再通过临时目录和原子替换保存。生成或推荐的命令继续经过终端控制链路。

默认模型路由仅启用 Linux 审查，H3C 模型需要单独准备端点与路由。其他平台的命令资料与规则可以独立于模型使用，平台适配和模型审查范围分别核对。

## 构建与部署

### 环境要求

| 用途 | 环境 |
| --- | --- |
| 源码构建与核心工作台 | Bash、uv、Python 3.10 / 3.11、Node.js 20.19+ 或 22.12+ |
| 常驻应用服务 | Linux x86_64、systemd，以及可连接目标设备的现有网络 |
| 默认本地 AI | Docker Compose、NVIDIA GPU、可供容器使用的驱动运行时，以及两个所需 GGUF 文件 |
| 可选知识库 | Agent 可选依赖与 Embedding 配置，按需启用 |

单独构建网页可在仓库根目录执行 `make build`。该命令按锁文件安装前端依赖，构建网页，并执行生产资源与 Chromium 80 兼容检查。

### 首次安装到服务器

准备好系统工具、两个模型文件及 Compose 配置中固定摘要对应的镜像，再在源码目录执行：

```bash
./scripts/quickstart.sh --build-only
sudo ./deploy/server/install.sh --address '<server-ip>' --models '/path/to/models' --uv "$(command -v uv)"
sudo systemctl start auditbox-server-{proxy,gateway,models,inference,agent}
```

`<server-ip>` 替换为服务器 IPv4 地址，`/path/to/models` 替换为放置两个默认模型的实际目录。首次安装脚本校验模型文件、创建 release、专属账号、独立 Python 环境与 systemd 单元，并为新环境生成随机凭据。安装所用系统 `python3` 须为 3.10 或 3.11。

浏览器访问 `http://<server-ip>:18080`。初始账号为 `opsadmin` 和 `superadmin`，随机密码保存在仅 root 可读的 `/etc/auditbox-server/initial-credentials.json`。模型启动器先等待 Linux 审查模型健康，再启动问答模型，两个模型就绪后继续运行 Inference 和 Agent。

这组安装步骤用于新实例。已有实例按[服务器部署文档](deploy/server/README.md)备份配置和数据库，再进行升级或回退。部署文档还包含镜像准备、健康检查、日志查看与开机自启动的处理。

### 运行数据与版本管理

| 内容 | QuickStart／本地开发 | 常驻安装 |
| --- | --- | --- |
| 核心配置与随机凭据 | `box/.env` | `/etc/auditbox-server/` |
| 核心业务与审计数据 | `box/data/` | `/var/lib/auditbox-server/` |
| Agent 会话、运行与文件 | 按 Agent 的本地数据配置保存 | 安装器配置的持久化数据目录 |
| 源码与 Python 环境 | 仓库内各模块的独立环境 | `/opt/auditbox-server/releases/<version>/` |
| 当前应用版本 | 当前源码目录 | `/opt/auditbox-server/current` 版本链接 |

常驻安装将配置、模型和业务状态与应用版本分开保存。每个 release 使用独立 Python 环境，回退时选择对应源码与依赖；数据库与配置需要单独备份，应用回退不会逆向迁移数据库。

## 使用边界与部署注意事项

- **操作权限**：目标账号决定能在设备上执行的操作；AuditBox 的确认、阻断与工具审批在工作台链路内生效。规则覆盖需要结合实际设备平台核对。
- **模型判断**：模型提供分析、建议与候选动作，判断依据需要结合当前设备输出。相关模型卡说明用途、已知边界和现有记录。
- **内部接口**：浏览器请求由 Gateway 认证。Agent 无独立登录鉴权，Agent、Proxy、Inference 与模型端点应保持回环监听。
- **外部连接**：本地模型部署、外部模型、MCP 和其他扩展使用各自的地址与权限。启用外部服务前核对其接收的上下文和可访问资源。
- **数据留存**：审计使用脱敏和有限摘要保留依据，原始输出中无标识的秘密仍需操作员核对。配置、数据库、附件与导出文件按业务数据管理。

凭据管理、部署访问范围与问题报告方式见[安全说明](SECURITY.md)。

## 本地开发

先按 QuickStart 准备构建与配置；仅准备环境可使用 `--build-only`。开发各模块时，在仓库根目录执行：

```bash
make setup
```

该命令安装后端、Agent 开发工具与前端依赖，不启动服务。核心工作台使用 `./scripts/quickstart.sh --start-only`；单独调试 Proxy 或 Gateway 可用 `make run-proxy`、`make run-gateway`，先停止组合启动以免端口冲突。

AI 与前端开发按需启动以下服务，并从 `agent/.env.example`、`web/.env.example` 创建所需配置，保留已有 `.env`：

| 工作目录 | 命令 |
| --- | --- |
| `box/` | `uv run --frozen --python 3.11 auditbox-inference` |
| `agent/` | `uv run --frozen --python 3.11 auditbox-agent` |
| `web/` | `npm run dev` |

模型进程按[模型说明](models/README.md)另行启动，前端开发示例连接 `127.0.0.1:18080`。后端与 Agent 分别使用各自的 Python 环境和 `uv.lock`，前端使用 `web/package-lock.json`。

依赖变更、验证入口与提交要求见[贡献指南](CONTRIBUTING.md)。
